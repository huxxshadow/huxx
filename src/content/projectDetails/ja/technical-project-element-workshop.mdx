## 担当

個人プロジェクトです。シミュレーションとレンダリングをすべて GPU で行うフォーリングサンド系サンドボックスで、世界は 512 × 288 のセルオートマトンです。各セルが砂の一粒、水の一滴、煙のひとすじ、あるいは固体の一部になります。

- **シミュレーション**：セルの移動、44 種類の反応、熱伝導、潜熱を伴う相変化、流体と煙の場、剛体を GPU のコンピュートパスで実装しました。Godot の物理エンジンは使っていません。
- **レンダリング**：Radiance Cascades による 2D グローバルイルミネーション、通過した物質の色に染まる光、サブサーフェススキャタリング、そしてライティングで平面の世界に奥行きを与える 2.5D ビュー。
- **最適化**：数多くの最適化によって、1 フレームあたりの GPU 時間を 3.5 ms に短縮し、全フレームの出力をバイト単位で同一に保ちました。

## ライティング

ライティングは **Radiance Cascades** による 2D グローバルイルミネーションです。どのセルも光を放つことができ（火、溶岩、ランプ、発光する物質）、どのセルも RGB の 3 チャンネルで光を減衰させます。そのため緑の塩酸、青い水、赤いガラスを通った光は色づき、壁に色のついた光を落とします。氷、結晶、ゼリーのような半透明の物質では光が内部で散乱し（サブサーフェススキャタリング）、表面には鋭いハイライト用のクリアコート層があります。

グローバルイルミネーションとは別に、窓から差し込む日光、吊りランプの光束、鏡で反射した光束をそれぞれのパスで追跡し、最後にブルーム、自動露出、AgX トーンマッピング、カラーグレーディング LUT で仕上げます。

## シミュレーション

各セルは材質、温度、寿命、フラグを 1 つの `rgba32ui` テクセルに格納します。移動には **Margolus 2 × 2 ブロック** を使います。グリッドを重ならないブロックに分け、各スレッドが自分のブロックの 4 セルだけを並べ替えるので、書き込みの競合が起きません。1 tick に 8 回のサブステップがあり、ブロックの位置を交互にずらします。空気も物質の一つなので、粉体、液体、気体の浮き沈みは同じ密度比較で決まります。

反応は反応物ペアの 256 × 256 ルックアップテーブル（確率と温度範囲つき）から引き、各ブロック内で隣り合うペアごとに評価します。熱はセル間で拡散し、相変化は潜熱を吸収または放出します。1/4 解像度の流体ソルバーが熱い空気の浮力と爆風を、1/2 解像度の媒質場が煙、蒸気、炎を扱います。

## 2.5D ビュー

形は常に二次元のままで、奥行きはライティングだけで表現します。最終画像は 1 本のビューシェーダーが合成します。各ピクセルの視線は、数セルの厚みを持つ板として扱うプレイ層を通り、続いて窓、柱、岩壁からなる背景のレリーフを通ります。

- **レリーフ法線**：輪郭が光の方へ傾いたり離れたりして、縁が浮き彫りのように光を受けます。
- **界面**：水、ガラス、氷の表面で視線が屈折率に従って曲がり、フレネル反射はシーンへ追跡し直されます。
- **背景**：レリーフは奥行きに応じてぼかした光で照らされ、前景の影、水の後ろのコースティクス、接触による遮蔽が入ります。
- **空気感**：層の間の霞、空気遠近法、昼夜のサイクル、カメラ移動時のわずかな視差。

## パフォーマンス

1 フレームの予算は 16 ms（60 fps）です。ライティングの効果は一つずつ追加していき、追加するたびに重くなったので、最適化は最後にまとめて行うのではなく、開発全体を通して続けました。以下は行った順に並べた各ステップです（RTX 5090、ワールド 512 × 288）。

### ステップ 1：1 ミリ秒ごとの行き先を見えるようにする

まずゲーム内のパフォーマンスパネル（F3）を作りました。

- **パスごとの時間**：各レンダリングパスの GPU ミリ秒を棒グラフで表示します。
- **コストヒートマップ**：2.5D ビューのシェーダーが背景・空気・前景のサンプル数をピクセルごとに数えて画面に重ね、物質ごとのミリ秒に換算します。どの物質が一番重いかが一目でわかります。
- **効果ごとのコスト**：各効果を順番に短時間オフにし、オン／オフの差から実際の GPU 時間を測ります。

### ステップ 2：ピクセル単位の処理をワールド解像度へ移す

ヒートマップで一番重かったのは前景のボリュームフォグでした。最終画面の全ピクセルでディザ付きのレイマーチをしていたのです。フォグや光の筋はもともと滑らかで、そこまでの解像度は要らないため、512 × 288 のワールド解像度でフォグのテクスチャを事前計算し、合成時にバイリニアでサンプリングするようにしました。合成は約 1.0 ms から 0.13 ms に、光と影のギャラリーはフレーム全体で 1.88 ms から 0.93 ms になり、ディザのノイズも消えました。

### ステップ 3：光線ビームを半解像度に

反射・屈折ビームを入れると、今度はビームが一番の負荷になりました。ビームは経路に沿ってエネルギーをアトミック加算でバッファに積むため、アトミック書き込みの競合が主なコストでした。

- 蓄積バッファを半解像度にしました。
- 2 ステップごとに 1 回だけ積み、4 セルへのバイリニア分配もやめたので、アトミック書き込みは約 1/8 になりました。
- その後のブラーも半解像度の 3 × 3 で行います。

光学台はフレーム全体で 1.58 → 1.05 ms、ギャラリーは 1.29 → 0.94 ms、実験室は 1.08 → 0.86 ms になりました。ランプのビームには安価な事前判定も加えました。まず直線で 56 セル先まで調べ、透明な物や鏡がなければその光線は丸ごと飛ばします。分散する物質に入ったときだけ波長ごとに分け、それ以外は白色光 1 本だけを追跡します。

### ステップ 4：「絵が変わらない」ことを守る回帰テスト

その後、太陽光のウェーブフロントと 8 バンドのスペクトル分散を追加し、昼のシーンは 5.5～7.9 ms まで増え、そのうちビームだけで 3.4 ms 以上を占めました。ここから先はシェーダーの実行方法そのものを変えることになるので、絵を壊さないことを保証する必要がありました。

固定フレームレートではゲームは決定的です（シミュレーションの乱数は tick をシードにしています）。つまり結果を変えない最適化なら、元の絵を正確に再現できるはずです。そこで `perf_check.py` を書きました。9 つのシーン（ライティングが最も重いマップ、炎のシーン、スクリプトのデモ）を固定タイムステップでそれぞれ 240 フレーム描画し、後半のパスごとの時間を平均したうえで、各スクリーンショットを変更前の参照画像と**バイト単位**で比較します。1 ピクセルでも違えば最大誤差を報告し、すべて一致した変更だけを残します。

### ステップ 5：ビームを直列から並列へ

パスごとの計測で、2 つの直列の連鎖が見つかりました。

- **8 つの波長を順番に計算**：グループ内の 1 本でも分散するガラスに当たると、グループ全体が 8 波長を一つずつ追跡していました。これを波長ごとにワークグループの層（`gl_WorkGroupID.z`）を割り当て、8 層を同時に走らせる形に変えました。ビームの蓄積は整数のアトミック加算で実行順に依存しないため、結果はビット単位で同じです。
- **太陽光の探索がフレーム中で最長の直列処理**：640 本の太陽光線を、それぞれ 1 スレッドが約 600 セル歩いて、光の進路を変える最初の物質を探していました。新しい `sun_probe.comp` では各光線を 32 ステップずつの区間に分け、区間ごとに 1 スレッドで並列に調べます。ヒット位置は `0x7FFFFFFF − t` にエンコードし、`atomicMax` で最も手前のものを残すので、先頭から歩いた場合とまったく同じ答えになります。

| シーン | 変更前 | 変更後 |
| --- | --- | --- |
| ステンドグラスの広間（カバー） | 7.9 ms | 3.7 ms |
| 光学台 | 7.2 ms | 3.4 ms |
| 光と影のギャラリー | 6.8 ms | 3.3 ms |
| 実験室 | 5.4 ms | 3.1 ms |

### ステップ 6：シミュレーションを共有メモリへ

- **液体の横方向の広がり**：液体は 1 行を走査しながら動くので、走査は直列でなければなりません。以前は各スレッドがグローバルな画像を 1 セルずつ読み書きしていました。今は 64 セルの行区間ごとに 1 つのワークグループが担当し、64 スレッドがその区間と下の支えのセルを共有メモリへ並列に読み込み、1 スレッドがそこで同じ直列走査を行い、グループ全体で書き戻します。0.18～0.25 ms → 0.05 ms。
- **圧力の求解**：流体の圧力はポアソン方程式をヤコビ反復で解いており、以前は反復ごとに 1 回、計 20 回のディスパッチでした。128 × 72 の圧力グリッドは 1 つのワークグループの共有メモリに収まるため、1024 スレッドのワークグループ 1 つが共有メモリ上で全反復を実行し、近傍マスクは事前に計算しておきます。和を取る順序も元と同じなので結果は一致します。0.18 ms → 0.09 ms。これより大きいグリッドは従来の経路を使います。
- **アイドルなパス**：プレイヤーの入力がない tick では、コマンドパスはグリッドをそのままコピーするだけなので飛ばします。

シミュレーション全体は 2 倍速くなり、出力はやはりバイト単位で同じです。

### 結果

最も重いシーン、1536 × 864 で、1 フレームあたりの GPU 時間は **7.9 ms から 3.5 ms** になり、9 シーンすべての絵が最適化前とバイト単位で一致しています。
