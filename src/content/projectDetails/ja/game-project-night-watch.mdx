## 担当した役割

『ナイトウォッチ』は、私がネットイース（NetEase）で進めた実験的な課題で、AIネイティブなゲームプレイとAIゲーム開発のワークフローに焦点を当てています。モデルがコンテンツ制作に参加できるとき、それに見合う遊びの構造と開発フローをどう組み立てるか。主に次の業務を担当しました：

* **AIネイティブなゲームプレイ設計**：モデルがランタイムにコンテンツを生成できる能力を土台に、キャラクター・装備・素材・地点・イベント・状態をカードに統一し、コンテンツ拡張がインターフェースに依存しにくい形にしました。ランダム遭遇は結果を直接明かさないリスクのある選択として設計し、テキストの変奏を遊びの中核となる変数にしています。
* **LLMランタイムのコンテンツパイプライン**：イベントカードと敵カードの生成プロトコルを設計しました。構造化出力、整合性チェック、コンテンツのホワイトリスト、レベル帯、文体とネタバレ防止の制約、二次チェック、キャッシュとタイムアウト時のフォールバックを含み、「創造性はモデル、ルールと数値はコード」を実現しています。
* **AIとの協働とコンテンツ統合**：文体と美術の規範を定め、プログラム・美術・音楽・シナリオにわたるAI生成と人手によるレビューのフローを構築しました。80枚のカード素材を3段階のサイズに統一し、すべてのコンテンツをReact・Zustand・Three.jsのフロントエンドに統合しました。

## プロジェクト詳細

『ナイトウォッチ』は、ヴィクトリア朝ゴシックを題材とした **AIネイティブ・カードローグライク**です。中核にあるのは、遊び方が直感的でありながら十分なシステム的深さを備えたカードフレームワークの上に、コンテンツ・数値・ルールの厳密な制約を定義することで、AIが生成するコンテンツを局内のランダム拡張へ安定して参加させるという発想です。これにより、豊富な局外成長と局内のビルド変化を備え、従来のローグライクでは到達しがたい、真の意味でほぼ無限のビルドの可能性を実現します。

ゲームはWeb上で動作します。プレイヤーはランプを提げた夜警人として危険な列車に乗り込み、冷たく湿った通路、一等客室、食堂車、ボイラー室、そして霧に呑まれた車両を進みながら、戦いのたびに生き延びる術を探します。

遊びのフレームワークとして、『ナイトウォッチ』は『Stacklands』と『Cultist Simulator』のカードインタラクション設計を参考にし、キャラクター・装備・素材・地点・イベント・状態といった要素をすべてドラッグ可能なカードオブジェクトへ統一的に抽象化しました。「カードを使用スロットへドラッグする」という単一の操作で、合成・装備・地点への進入・アイテム使用といった中核行動が完結します。

### すべてがカード

独立したインベントリ画面も、鍛冶画面も、マップ画面もありません。スロットに置いたときにどの動作が解放されるかは、そのカード自身の種別だけで決まります。

* 素材 → **合成**（レシピが揃えば装備を作れる）
* 装備 → **装備**（メインハンド、オフハンド、頭、身体、手、装飾品2枠へ）
* 地点 → **進入**（その車両カードを一回のダンジョン進行として扱う）
* 消耗品 → **使用**（救急セットなどの即時回復）

### 戦闘

戦闘は自動進行のターン制です。装備は自動で効果を発揮し、プレイヤーは戦闘中に操作できず、長押しで早送りできるだけです。これは簡略化ではなく、意思決定を意図的に前倒しした設計で、勝敗は車両に入る前にほぼ決まっています。

中核となる駆け引きはダメージタイプと耐性です。ゲームには打撃・刃物・火器、そして人ならざる敵に効く光属性があり、敵は二つに分かれます：

* **人間の敵**（ずぶ濡れの男、潜む殺し屋、銃を選ぶ殺し屋、機械に巻き込まれた乗務員）は刃物と火器に弱いことが多く、湿り気や機械化の特徴があれば火への弱点が加わります。
* **人ならざる敵**（囁く者、霧の怨霊、あってはならぬもの、霧の主）は通常の物理攻撃と霧ダメージに高い耐性を持ち、光・銀・火でなければ有効に対処できません。

そのため、地点カードは本質的にどれも装備選びの問題です。「怪異の囁き」に入る前なら銀の十字架と風防ランタンを、「機械室」に向かうなら歯車の棍棒とパイプレンチのほうが有効です。装備選択の代償は瞬間的な操作には表れず、戦闘の始まりから結果を左右し続けます。

### 合成・接頭辞・解体：失敗を積み重ねに変える

素材は成長ループの中核です。歯車、銀、火薬、霧の精髄など13種の素材が車両ごとに分布しており、プレイヤーは目的に応じて探索ルートを選ぶことになります。

合成した装備にはレアリティに応じてランダムな接頭辞が付きます。鋭い、銀象嵌の、霧蝕の、といった具合で、同じレシピからでも異なる結果が生まれます。不要な装備は解体して素材に戻し、再び合成に回せます。

### ダンジョン構造：二択の進行と、隠された結果

地点カードに入ると、一歩ごとに二つの遭遇から一つを選んで向き合います。遭遇には戦闘と非戦闘（物漁り、罠、祠への献げ物、囁きの誘惑など）があります。イベントの描写は兆しと雰囲気だけを描き、報酬やダメージ、戦闘になるかどうかは明かさないため、プレイヤーは直感と車両の特質への理解で賭けるしかありません。一部の車両からは、特質がより極端でドロップがより絞られた支線も分岐し、次の装備のためにあえて回り道をする選択肢になります。

### ローグライクのメタ進行：前局の経験を「開始時のカード」に変える

一局が終わるたび、踏破したかどうかにかかわらず経験値が精算され、「夜警人レベル」が上がります。レベルアップで解放されるのは数値ではなく、次の一局の開始時に牌卓へ配られるボーナスカードです。最大HPを上げる「強靭な体躯」、防毒マスクを着けた状態で始められる「夜警の警戒」、血晶を一つくれる「霧中の拾遺」などがあります。メタ進行を数値ではなくカードで表すことで、世界観とインターフェースの一貫性を保っています。

### LLMによるランタイム生成：創造はモデルに、ルールはコードに

技術面での中核は、イベントカードと敵カードの**ランタイムLLM生成パイプライン**です。車両に入るたび、遭遇は静的プールからではなくモデルがその場で書き起こすこともあります。ただしパイプライン全体は厳しく制約されています。

* **構造制約**：JSONのみ出力、説明は禁止。各イベントは `kind`（戦闘 / 通常）を宣言し、kind は description と結果と一致しなければならない——戦闘として書いたなら本当に戦闘を発生させる。1バッチはおよそ半数が戦闘、半数が通常。
* **コンテンツのホワイトリスト**：アイコン、付与可能アイテム、敵定義ID、行動IDはすべてホワイトリストと互換表から選ぶ。ドロップテーブルはコードが指定し、モデルは選べない。
* **数値の主権はコードにある**：モデルが書くHPや攻撃力は指定されたtier区間に収まればよく、実際の値はコードがrollする。**モデルが責任を負うのはテキストの質だけ。**
* **文体制約**：華麗で、抑圧的で、神秘的で、わずかにクトゥルフ的。レトロなスチームパンク語彙（緑青、漆塗りの木、ガス灯、蒸気、湿気、囁き）を用い、現代語や興を削ぐ比喩は禁止。二人称で語り、「異常は目撃されるが説明されない」。
* **ネタバレ防止の曖昧化**：タイトルと description は雰囲気と兆しのみ。報酬、ダメージ、戦闘の有無を明示してはならない。戦闘イベントはそのダンジョンの敵の雰囲気に寄せつつ、フルネームを呼ばず結果も明かさない。
* **二次校正パス**：生成後に別の「校正員」プロンプトを走らせ、文体、曖昧さ、敵の雰囲気との整合を点検し、その局で既に配ったのと重複する装備ドロップを未出のものへ差し替える。
* **文脈認識**：生成時にはプレイヤーのビルド傾向（火器ルート、光を積んで非人を制する、近接の刃物・打撃、素手）、現在の逼迫度（長期の低HP）、直近の選択と直近の敵を渡し、テキストがこの一局の実情に寄り添うようにしている。
* **フォールバックとキャッシュ**：生成結果はキャッシュプールに入り、任意に引き直せる。タイムアウトや失敗時は静かに静的プールへ縮退し、プレイヤーはエラーではなく少し行儀のよいカードを見るだけになる。
