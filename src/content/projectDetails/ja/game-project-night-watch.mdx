## 担当した役割

『ナイトウォッチ』は、私がネットイース（NetEase）で進めた実験的な研究課題であり、**AIネイティブゲーム**と **AIゲーム開発ワークフロー**を探るものです。コンテンツ生産をモデルに委ねられるとき、ゲームプレイ自体はどうあるべきか、開発の進め方はどう組み立てるべきか。私が主に担当したのは次の領域です。

* **AIネイティブなゲームプレイの研究と設計**：「コンテンツはモデルがランタイムに生成できる」という前提から遊びの構造を逆算しました。キャラクター・装備・素材・地点・イベント・状態をすべてカードに統一して新規コンテンツが新しい画面を必要としないようにし、ランダム遭遇を「雰囲気だけを描き結果を明かさない賭け」として設計することで、モデルが最も得意とするテキストの変奏をそのまま遊びの変数に変えています。
* **ゲーム基盤フレームワークの設計**：カードのデータモデルと「使用スロットへドラッグ → 合成 / 装備 / 進入 / 使用」という単一の操作導線を設計し、戦闘、装備スロット、ダメージ属性と耐性、ダンジョン進行、メタ進行といったシステムの階層と境界を切り分けて、コンテンツが増え続けてもコアロジックに手を入れずに済むようにしました。
* **LLMランタイム生成パイプラインの設計**：イベントカードと敵カードの生成プロトコル（JSONのみ出力、`kind` と結果の整合チェック、ホワイトリストとtier区間、数値はコードがroll、文体とネタバレ防止の制約、二次校正パス、キャッシュプールとタイムアウト時のフォールバック）を設計し、文章の創造性はモデルに、ルールと数値はコードに残しました。
* **AI協働ラインと統合**：文体基調とアート仕様を定め、プログラム・アート・音楽・シナリオ各工程のAI生成と人によるレビューを一本のラインにつなぎ、80枚のカードアートを3段階の解像度で統一して、React + Zustand + Three.js のフロントエンドへ統合しました。

## プロジェクト詳細

『ナイトウォッチ』は、ヴィクトリア朝ゴシックを題材とした **AIネイティブ・カードローグライク**です。中核にあるのは、遊び方が直感的でありながら十分なシステム的深さを備えたカードフレームワークの上に、コンテンツ・数値・ルールの厳密な制約を定義することで、AIが生成するコンテンツを局内のランダム拡張へ安定して参加させるという発想です。これにより、豊富な局外成長と局内のビルド変化を備え、従来のローグライクでは到達しがたい、真の意味でほぼ無限のビルドの可能性を実現します。

ゲームはWeb上で動作します。プレイヤーはランプを提げた夜警人として危険な列車に乗り込み、冷たく湿った通路、一等客室、食堂車、ボイラー室、そして霧に呑まれた車両を進みながら、素材を集め、装備を合成し、ビルドを組み替え、遭遇に対処して、戦いのたびに生き延びる術を探します。

遊びのフレームワークとして、『ナイトウォッチ』は『Stacklands』と『Cultist Simulator』のカードインタラクション設計を参考にし、キャラクター・装備・素材・地点・イベント・状態といった要素をすべてドラッグ可能なカードオブジェクトへ統一的に抽象化しました。「カードを使用スロットへドラッグする」という単一の操作で、合成・装備・地点への進入・アイテム使用といった中核行動が完結します。これは操作理解のコストを下げると同時に、以降のコンテンツ拡張に高度に統一されたインターフェースを与えます。新規コンテンツは複雑な画面を新設する必要がなく、新しいカード種別またはカードデータとしてシステムへ接続するだけで済みます。

ひとつ補足があります。このページ上部の **Play** から遊べるWeb体験版は、現在AIバックエンドサービスを配置していないため、イベントカードと敵カードはリアルタイム生成されず、あらかじめ用意した静的カードプールから供給されます。システム・進行・数値はすべて完全に遊べる状態で、変わるのはランダムコンテンツの幅が静的プール内に固定される点だけです。

### すべてがカード：ひとつの動詞と6種のカード

独立したインベントリ画面も、鍛冶画面も、マップ画面もありません。スロットに置いたときにどの動作が解放されるかは、そのカード自身の種別だけで決まります。

* 素材 → **合成**（レシピが揃えば装備を作れる）
* 装備 → **装備**（メインハンド、オフハンド、頭、身体、手、装飾品2枠へ）
* 地点 → **進入**（その車両カードを一回のダンジョン進行として扱う）
* 消耗品 → **使用**（救急セットなどの即時回復）

そのためチュートリアルも極端に短く、2ステップで済みます。歯車2つを歯車棍に合成し、それをメインハンドに装備する——それだけで全操作を学べます。

### 戦闘：判断を準備段階へ前倒しする

戦闘は自動進行のターン制です。装備の効果は自動で適用され、プレイヤーは戦闘中に操作できません（長押しで加速のみ）。これは手抜きではなく、明確な設計上の取捨選択です。**あらゆる判断は、車両の扉を開ける前の時点へ前倒しされます。**

本当の駆け引きはダメージ属性と耐性のマッチングにあります。属性は打撃・刃物・火器、そして非人に有効な光の4種。敵は2つの陣営に分かれます。

* **人間側**（ずぶ濡れの男、潜む殺し屋、銃を選ぶ殺し屋、機械に巻き込まれた乗務員）——多くは刃物と火器に弱く、濡れたものは火を嫌い、機械化したものは焼かれると脆い。
* **非人側**（囁く者、霧の怨霊、あってはならぬもの、霧の主）——物理と霧のダメージはほとんど通らず、光・銀・火だけがその輪郭を散らせる。

こうして地点カードは装備構成のパズルになります。「囁き」の車両へ入る前には銀十字と防風ランタンを持ちたくなり、「機械室」では歯車棍とパイプレンチが頼りになる。装備を誤った代償は操作ミスではなく、1ターン目から結果が決まってしまうことです。

### 合成・接頭辞・解体：失敗にも何かを残させる

素材はこの循環の血液です。歯車、錆びた鉄片、革、火薬、ガス、血晶、銀、布、ガラス、鉄塊、ランプ油、霧骨灰、霧の精髄——13種の素材はそれぞれ車両の特質に紐づいています。湿った区画は革と鉄片を、機械室は歯車を、神龕は銀を与え、霧の精髄は最も濃い霧の底でしか凝りません。

合成された装備には**レアリティに応じたランダムな接頭辞**が付きます。鋭い、頑丈な、精鋳の、銀象嵌の、霧蝕の、血に浸した——同じレシピからまったく同じ一本が出ることはなく、「もう一本打つ」理由が常に残ります。解体は逆方向の導線を提供し、合わなくなった装備を素材へ戻して次の合成に回せます。

狙いは**失敗を沈殿させること**です。食堂車で倒れた一局はレベルを持ち帰れませんが、レシピと耐性と車両特質への理解、そして次の一局のより賢い初手を残します。

### ダンジョン構造：二択の進行と、隠された結果

地点カードに入ると、進行は**一歩ごとに二つの遭遇から一つを選ぶ**形になります。遭遇は戦闘と非戦闘に分かれ、物色、罠、神龕への供物、囁きの誘惑、ひと息つける物陰などがあります。そしてカード面に書かれているのは、雰囲気だけです。

これはイベント設計で私が定めた厳格なルールです。**description は兆し・匂い・物音だけを描き、何が手に入るか、何点減るか、戦闘になるかを決して明示しない。**「壁際の影に埃をかぶった木箱が置かれ、真鍮の留め金は緑に錆びている」——それは救急セットかもしれないし、待ち伏せかもしれません。プレイヤーは報酬を読んで確定を押すのではなく、直感と車両特質への理解に賭けることになります。

いくつかの車両からは支線が分岐します。機械室は一等客室から、貨物車は連結部から、礼拝堂と霧の車両はボイラー室から。支線は特質がより極端で、ドロップもより専門的です。次の装備構成のためにプレイヤーが自ら選ぶ回り道になっています。

### ローグライクのメタ進行：前局の経験を「開始時のカード」に変える

一局が終わるたび——踏破しても途中で倒れても——経験値が精算され、「夜警人レベル」が上がります。レベルアップで解放されるのは数値ボーナスではなく、**次の一局の開始時に手元へ配られる一枚のカード**です。強靭な体躯は最大HPを、闘争本能は攻撃力を上げ、夜警の警戒は防毒マスクを装備した状態で始めさせ、行嚢と備糧は素材を追加で与え、霧中の拾遺は血晶を一つ握らせます。

メタ進行を数値ではなくカードとして表現したのは、世界観とインターフェースの一貫性を保つためです。リザルト画面に出るのは「新たに解放された初期カード」であり、次の一局ではそれが本当に牌卓の上に置かれています。

### LLMによるランタイム生成：創造はモデルに、ルールはコードに

技術面での中核は、イベントカードと敵カードの**ランタイムLLM生成パイプライン**です。車両に入るたび、遭遇は静的プールからではなくモデルがその場で書き起こすこともあります。ただしパイプライン全体は厳しく制約されています。

* **構造制約**：JSONのみ出力、説明は禁止。各イベントは `kind`（戦闘 / 通常）を宣言し、kind は description と結果と一致しなければならない——戦闘として書いたなら本当に戦闘を発生させる。1バッチはおよそ半数が戦闘、半数が通常。
* **コンテンツのホワイトリスト**：アイコン、付与可能アイテム、敵定義ID、行動IDはすべてホワイトリストと互換表から選ぶ。ドロップテーブルはコードが指定し、モデルは選べない。
* **数値の主権はコードにある**：モデルが書くHPや攻撃力は指定されたtier区間に収まればよく、実際の値はコードがrollする。**モデルが責任を負うのはテキストの質だけ。**
* **文体制約**：華麗で、抑圧的で、神秘的で、わずかにクトゥルフ的。レトロなスチームパンク語彙（緑青、漆塗りの木、ガス灯、蒸気、湿気、囁き）を用い、現代語や興を削ぐ比喩は禁止。二人称で語り、「異常は目撃されるが説明されない」。
* **ネタバレ防止の曖昧化**：タイトルと description は雰囲気と兆しのみ。報酬、ダメージ、戦闘の有無を明示してはならない。戦闘イベントはそのダンジョンの敵の雰囲気に寄せつつ、フルネームを呼ばず結果も明かさない。
* **二次校正パス**：生成後に別の「校正員」プロンプトを走らせ、文体、曖昧さ、敵の雰囲気との整合を点検し、その局で既に配ったのと重複する装備ドロップを未出のものへ差し替える。
* **文脈認識**：生成時にはプレイヤーのビルド傾向（火器ルート、光を積んで非人を制する、近接の刃物・打撃、素手）、現在の逼迫度（長期の低HP）、直近の選択と直近の敵を渡し、テキストがこの一局の実情に寄り添うようにしている。
* **フォールバックとキャッシュ**：生成結果はキャッシュプールに入り、任意に引き直せる。タイムアウトや失敗時は静かに静的プールへ縮退し、プレイヤーはエラーではなく少し行儀のよいカードを見るだけになる。

このパイプラインが体現しているのは一つの設計上の立場です。**LLMは雰囲気とテキストの無限の変奏に向くが、ゲームのルールの裁定者には向かない。** だから私はそれを最外層に置きました。「隅に木箱がある」を千通り書かせることはできても、箱の中身、失うHP、戦闘の決着は常にコードが決めます。

### 表現レイヤーと画質設定

フロントエンドは React + Zustand + Immer で状態を管理し、Three.js がカードのフリップ、配布、戦闘カメラを担当します。ブラウザ環境の性能差が大きいため、描画は4段階に分けました。**2Dテーブルのみ**（3Dオフ、低スペック機で最も滑らか）、**戦闘カメラなしの3Dカード**、**スーパーサンプリング＋パーティクル半減**、そして**フル3D＋戦闘カメラ＋スーパーサンプリング＋フルパーティクル**。セーブ、音量、画質設定は localStorage に永続化され、エラーバウンダリは白画面で詰ませる代わりに「セーブをリセットして再読み込み」を提示します。

オーディオは、霧の夜を基調としたBGM、カードと戦闘の効果音一式、そして冒頭の引用に用いる3本のナレーション音声で構成されています。

### AI制作ライン：どこまでを一括生成したか

ゲーム内のコンテンツの大半は、AIワークフローを組み上げたうえで一括生成したものです。

* **カードアート**：80枚のカードイラスト（キャラクター12、装備24、素材13、地点15、イベント10種、メタ進行5、アイテム1）。スタイルを統一したうえで3段階の解像度に書き出し、素材ファイルは計240点。
* **カードテキスト**：静的イベントカード27枚、敵プリセット40種（地点特質8 × 5）の名称と登場ナレーション、装備24件と素材13種の説明文、接頭辞12種、そして各地点の情景描写と勝敗の結算テキスト。
* **ローカライズ**：中国語と英語、2セットの完全なテキスト。UI文字列およそ340項目に加え、カードテキスト全文。
* **オーディオ**：霧の夜を基調としたBGM1曲、カードと戦闘の効果音8点、冒頭引用のナレーション音声3本。
* **プログラム**：React + Zustand + Immer + Three.js によるフロントエンド実装。カード操作、戦闘処理、合成と解体、セーブ、画質設定まで。

私が担当したのは、まずルール・数値・構造の骨格（カード種別、ダメージと耐性、ドロップテーブル、地点特質、生成プロトコル、文体制約）を組み上げ、その骨格が許す形の中でAIにコンテンツを量産させ、最後に一点ずつ検分・差し替え・再利用することでした。
