## 担当した役割

7日間の個人練習プロジェクトとして、Unreal Engine 5 上でパルクールのモーションとカメラのシステムをゼロから構築しました。アニメーションアセットを除き、ゲームプレイシステム、カメラ挙動、コードはすべて私が担当しています。

* **モーションシステムの設計と実装**：パルクールを踏破、壁走りと壁ジャンプ、ジャンプと着地、スライディング、スプリント、空中制御、旋回ブレンドといったモジュールに分解し、それぞれを独立したキャラクターコンポーネントとして実装。各フレームで速度と状態を書き込む権限を明示的に定め、モジュール同士が衝突しないようにしました。
* **3Cのチューニング**：「リアルに走る」ではなく「気持ちよく走る」を基調に据え、速度ティア、状態の出入り条件とクールダウン、アニメーションとコードの分担境界を設計。プレイヤーが知覚できる量にはすべて調整用パラメータを用意しました。
* **カメラシステムとカメラ演出**：速度・状態・イベントで駆動するカメラダイナミクスを実装。ラグ、FOV、アーム長、ドリーズーム、旋回時の構図、歪み、シェイク、空中の構図、視点ウィンドウまでを網羅し、カットシーンや演出スクリプトから再利用できるカメラチャンネルを外部に公開しました。
* **タイムスケーリングとビート設計**：ジャンプ頂点でのスローモーションを実装。通常版と誇張版の2プロファイルとキャラクター単位の時間補償によって、「最高点」という瞬間を演出として組み立てられるビートに変えました。
* **デバッグと検証ツール**：リーダー／フォロワー2体のデモリグを作成。開演時に両者のカスタムコンポーネントの編集可能プロパティをすべて自動比較し、差分を画面上に列挙することで、チューニングの結果を議論ではなく検証で確かめられるようにしました。

## プロジェクト詳細

『パルクール・モーションシステム』は、パルクールゲームのモーションシステムと3C設計を一通り通しで作ってみるために、7日間で仕上げた Unreal Engine 5 の練習プロジェクトです。参照したのは私の好きな『Ghostrunner』と『Mirror’s Edge』。この2本に共通するのは、**動きが物理的に妥当かどうかはほとんど問題ではなく、速度が途切れないこと、そしてカメラが「自分は飛んでいる」と信じさせることこそが重要**だという点です。

### 前提：リアリティを捨ててスピード感を取る

最初に定めた原則はシンプルです。**手触りと物理的リアリティが衝突したら、無条件でリアリティを譲る。** この原則は実装の随所に具体的な形で残っています。

* **壁走りは移動モードを切り替えない**：キャラクターは終始 `MOVE_Falling` に留まり、`GravityScale` をゼロにしたうえでコンポーネントが毎フレーム速度を丸ごと上書きします。壁に沿った「まず水平、その後沈む」という弧は、エンジンの重力積分の副産物ではなく自分で書いた調整可能なカーブです。代償として速度を直接書くことで CharacterMovement のネットワーク予測を迂回するため、このシステムはシングルプレイ専用になっています。
* **スライディングはルートモーションではなく速度で駆動**：スライドのループアニメは等速で進みますが、スライディングという動作の要点はまさに速度が減衰することにあります。そこでアニメーションは表現だけを担い、速度カーブはコードが持ちます。アニメーションが手触りに従うのであって、その逆ではありません。
* **踏破からクライミングを意図的に外す**：踏破はハードル、ヴォルト、マントルの3種に分類し、それぞれ「モンタージュを1本再生して終わり」という構造にしています。クライミングは「壁にぶら下がる」という持続状態と懸垂移動の状態機械一式を必要とし、このシステムが求める連続性に対してテンポを鈍らせるため、除外しました。

これらの取捨に共通する狙いは、**不確定性をシステムから追い出すこと**です。パルクールの手触りにとって最悪なのは「なぜ今回は前回と違う挙動になったのか」であり、コードで確定できる量は物理シミュレーションやアニメーションの副作用に委ねません。

### モーションシステム：コンポーネント単位の分割

移動能力はキャラクターに付く独立したコンポーネント群に分割され、それぞれが一つの役割を持ちます。

* **踏破**：前方の障害物をトレースして分類し（薄くて低い → ハードル、薄いが裏に地面がない → ヴォルト、厚い → マントル）、進入速度に応じて立ち／歩き／走りの3段階のモンタージュを選びます。このモジュールだけは逆に主導権をルートモーションと Motion Warping に渡します。踏破アニメ自体がワーピング用の窓を持っているため、コードで変位を計算するとかえって精度が落ちるからです。
* **壁走りと壁ジャンプ**：側面の壁を検出し、貼り付き状態と継続時間の上限を管理、壁ジャンプの方向と初速を処理します。
* **ジャンプと着地**：離陸の瞬間に水平速度をラッチし、立ち／歩き／走り／スプリントの4段階でアニメーションをブレンド。滞空中の最高点を追跡して落下高度を算出し、接地時にその高度から通常着地か受け身かを決めます。すべてのブレンド重みはラッチ値由来なので、空中で微調整しても滞空中ずっと安定します。
* **スライディング**：進入条件、速度減衰、離脱方法（立ち上がる／しゃがみ維持／しゃがみ歩き／歩いて出る／走って出る）を個別に設定でき、離脱方法はそのままアニメーションステートマシンが次に再生すべきクリップに対応します。
* **スプリントと空中制御**：スプリントは速度ティアの切り替えを担い、その強度をカメラの歪みへ渡します。空中制御は滞空中の旋回能力を個別に管理し、修正が浮つきすぎず固すぎない範囲に収めます。
* **旋回ブレンド**：その場旋回と移動中の向きの補間を扱い、8方向ロコモーションのブレンドスペースと組み合わせます。

キャラクター全体はステートツリーが統括し、GASP の8方向ロコモーションとリーンのブレンドスペースがアニメーション層を駆動します。自作コードはおよそ12,700行のC++で、9つのコンポーネントと1つのデモリグに分かれています。

### 3C：速度を書く者がそのフレームを支配する

コンポーネントが増えたときに壊れやすいのは個々の能力ではなく、複数が同時にキャラクターの速度を変えようとするフレームです。この項目では**状態ごとに権限者を1つだけ指名する**方針を採りました。

* 壁走り中はコンポーネントが CharacterMovement の後に tick し、毎フレーム速度を丸ごと上書きします。ステートツリーがそのフレームに何を入力していても上書き済みなので、移動は決定的になります。
* 踏破中はモンタージュのルートモーションが権限を持ち、コードは進入判定と収尾だけを担当します。
* スライディング中はスライドコンポーネントの速度カーブが権限を持ち、アニメーションは変位に関与しません。
* それ以外の時間は通常の入力駆動の移動に戻ります。

同じ考え方は状態の問い合わせにも適用されます。壁走りが意図的に `MOVE_Falling` に留まるのは、プロジェクト内の5か所が `IsFalling()` を読んでいるからです（着地の受け身、着地カメラシェイク、頂点スローの取り消し判定など）。`MOVE_Flying` に切り替えるとそれらが一斉に無効化されますし、そもそも「本当に空中にいて、ただ壁に手をついている」という意味論のほうが正確です。

### カメラ：まず速度を絵にする

カメラシステムはこのプロジェクトで最も規模の大きい部分（約2,800行）です。追従コンポーネントではなく、速度・状態・イベントが共同で駆動する複数のチャンネルの集合であり、各チャンネルは個別に調整も無効化もできます。

* **速度 → FOVとアーム長**：設定した速度帯の中で、速度をFOV増分とカメラの寄りにマッピング。任意でカーブによる整形が可能です。
* **速度駆動のカメララグ**：SpringArm にもラグはありますが静的な値です。ここではラグ速度を移動速度の関数にし、低速では密着、高速では緩めて、カメラがキャラクターの後ろに「振られる」ことで重量感を生みます。
* **ターンダイナミクス**：旋回時に構図オフセットと軽いロールを与え、強度は閾値でスナップするのではなく速度に応じて滑らかに減衰します。
* **レンズ歪み**：スプリント時にポストプロセスマテリアルで画面端をわずかに内側へ引き込みます。強度が追うのはスプリントキーの押下ではなく、走り／スプリント帯で補間した**実際の速度**です。歪みが語るべきなのは「本当に速くなった」ということだからです。
* **空中の構図**：上昇中はカメラを動かさず、頂点を過ぎてから落下側の効果を強めていきます。空中の旋回オフセットは別途スケールします。空中は水平速度が高くなりがちで、そのままだと行き過ぎるからです。
* **シェイク**：離陸、着地、長い落下にそれぞれ独立したシェイク設定を持たせています。

### カメラ演出：カメラを「組み立てられる言語」にする

このプロジェクトが本当に探りたかったのは、**カメラが受動的に追従するのではなく、能動的に語れるか**という点です。そのためカメラシステムは、ゲームプレイ・カットシーン・演出スクリプトから呼べる機能をいくつか公開しています。

* **ドリーズーム**：走り出しでカメラを寄せながらFOVを開き、背景を後方へ引き伸ばして推進感を作ります。補償強度は調整可能で、最大にすると主人公の画面内サイズが厳密に固定されズーム感は最も純粋になりますが、同時に最も酔いやすくもあります。0.6〜0.8 が「それらしさはあるが酔わない」あたりです。符号を反転すれば逆になり、背景が押し潰されて迫ってくる、「立ちすくむ／何かに気づく」ためのショットになります。走り出し条件からの自動発動（静止時間の要件とクールダウン付きで、歩いたり止まったりを繰り返してもズームし続けない）に加え、明示的に一度だけ呼び出してカットシーンや重要アイテムの取得に同じエンベロープを流用することもできます。
* **外部カメラチャンネル**：ロール、アーム長、FOV、構図オフセットの4チャンネルを外部から丸ごと引き取れます。しかも**各チャンネルが独自のフェードイン／フェードアウト時間を持ちます**。ここが最もカメラ言語に近い設計だと考えています。4つが同時に決まると機械的に見えますが、ロールは即座に追従し構図オフセットはゆっくり滑る、というズレこそが意識的なカメラワークらしく見えます。壁走りはこのチャンネルの最初の利用者で、−20°のロール、アーム長の短縮、FOVの拡張、横方向の構図オフセットを与えています。
* **視点ウィンドウ**：一定の間、プレイヤーが見られる方向の範囲を制限できます。ウィンドウは開いた瞬間にまず現在の視点を「包み込み」、その後設定値まで収束するため、ハードクランプによる跳びが起きません。ソフト境界の外では継続的に引き戻され、ハード境界は押し切れません。壁走り中はこれで視点を壁の向き付近に保ちます。これは本質的に**カメラの制約で注意を誘導する**ことであり、操作制限ではなく演出手段です。
* **タイムスケーリング**：ジャンプの頂点でグローバルな時間倍率を落として戻し、一拍の間を作ります。プロファイルは2種類。高所からの落下にはより長い滞空感が必要で、普通の小さなジャンプには短い句読点だけで十分です。さらに重要なのは、プレイヤーキャラクターだけ時間倍率を補償できる点です。世界を遅くしてプレイヤーは等速のままならバレットタイム、両方遅くすれば純粋なリズムの停止になります。発動前には下方向へ予測トレースを行い、どうせすぐ着地する場面で無意味なスローを出さないようにしています。

これらを組み合わせると、**頂点、走り出し、壁への貼り付きといった本来ゲームプレイ上の瞬間が、同時にカメラ上のアクセントにもなります。** 「ここは速い」「ここは危ない」とプレイヤーに告げる必要はありません。カメラがすでにそう言っています。

### 検証ツール：チューニングを目に見えるようにする

手触りのチューニングで最も難しいのは「今回何を変えたのか」を言葉にすることです。そこでデモリグを別途書きました。シーンにリーダーとフォロワーの2体を置き、フォロワーには指定した上書きで異なるパラメータを走らせます。開演時にリグが両者のカスタムコンポーネントの編集可能プロパティをすべてエクスポートして比較し、**差分をそのまま画面に列挙します**。

この方法で録った比較映像にはナレーションが要りません。画面そのものが「このテイクは何を見せているのか」を語っています。同じルートで、左右の違いは画面に並んだ数個のパラメータだけです。

### アセットの出典と自作範囲

アニメーションアセットは Unreal Engine の Game Animation Sample と Hammerhead の Dynamic Wall Run（壁走り系はリターゲット済み）を使用しています。ゲームプレイシステム、カメラロジック、コードはすべて自作です。
