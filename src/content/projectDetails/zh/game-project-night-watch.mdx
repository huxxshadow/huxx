## 我的职责

《守夜人》是我在网易推进的一项实验性课题，聚焦 AI 原生玩法与 AI 游戏开发工作流：当模型能够参与内容生产时，如何构建与之匹配的玩法结构与开发流程。我主要负责以下工作：

* **AI 原生玩法设计**：基于模型运行时生成内容的能力，将角色、装备、材料、地点、事件与状态统一为卡牌，降低内容扩展对界面的依赖；将随机遭遇设计为不直接揭示结果的风险选择，使文本变体成为可玩的核心变量。
* **LLM 运行时内容管线**：设计事件卡与敌人卡的生成协议，包括结构化输出、一致性校验、内容白名单、等级区间、文风与防剧透约束、二次校对、缓存及超时降级机制，实现“模型负责创意，代码负责规则与数值”。
* **AI 协作与内容集成**：制定文风与美术规范，搭建覆盖程序、美术、音乐和剧本的 AI 生成与人工审校流程；统一 80 张卡牌素材的三档尺寸，并将完整内容集成至 React、Zustand 与 Three.js 前端。

## 项目细节

《守夜人》是一款维多利亚哥特题材的 AI 原生卡牌 Roguelike。游戏的核心理念，是在一套玩法直观但具有足够系统深度的卡牌框架之上，通过定义严格的内容、数值与规则约束，让 AI 内容能够稳定地参与局内随机拓展，从而使游戏具备大量局外成长与局内构筑变化，并进一步实现传统 Roguelike 难以达到的、真正意义上的近乎无限的构筑可能。

游戏基于 Web 端开发，玩家将扮演一名提灯的守夜人，登上一列危险的列车，在湿冷走廊、头等舱包厢、餐车、锅炉房与被雾吞没的车厢之间不断前进，在一次次战斗中寻找存活下来的可能。

在玩法框架上，《守夜人》参考了《堆叠大陆》和《密教模拟器》的卡牌交互设计，将角色、装备、材料、地点、事件、状态等内容统一抽象为可拖拽的卡牌对象。玩家通过“将卡牌拖入使用槽”这一单一操作，完成合成、穿戴、进入地点、使用道具等核心行为。

### 卡即一切

游戏里没有独立的背包界面、锻造界面或地图界面，卡牌被拖进使用槽时解锁哪一个动作，只取决于它自身的类型：

* 材料 → **合成**（凑齐配方就能打造装备）；
* 装备 → **穿戴**（进入主手、副手、头部、身体、手部与两个饰品槽）；
* 地点 → **进入**（把这张车厢卡当作一次副本推进）；
* 消耗品 → **使用**（急救包一类的即时回复）。

### 战斗

战斗采用自动回合制：装备自动生效，玩家无法在战斗中操作，仅可长按加速。这并非简化设计，而是有意将决策前置——胜负往往在进入车厢之前就已决定。

核心博弈围绕伤害类型与抗性展开。游戏包含钝击、利器、火器，以及克制非人敌人的光属性；敌人则分为两类：

* **人类敌人**（湿透的男人、潜伏的杀手、挑枪杀手、被卷机械师）通常弱于利器与火器，潮湿或机械化特征还会带来额外的火焰弱点。
* **非人敌人**（低语者、雾中怨灵、非人之物、雾之主宰）对常规物理攻击与雾伤具有较高抗性，需要使用光、银或火才能有效克制。

因此，每张地点卡本质上都是一道配装题：进入「灵异低语」前，可以携带银十字与气死风灯；前往「机械间」时，齿轮短棍与管钳则更为有效。装备选择的代价不体现在即时操作上，而会从战斗开始便持续影响最终结果。

### 合成、词条与拆解：让失败有所积累

材料构成了成长循环的核心。齿轮、银、火药、雾之精粹等十三种材料分布在不同车厢，引导玩家根据目标选择探索路线。

合成装备会依稀有度获得随机前缀词条，如“锋利的”“银镶的”“雾蚀的”等，使相同配方也能产生不同结果。不需要的装备则可拆解为材料，重新投入合成。

### 副本结构：二选一的推进与被隐藏的结果

进入一张地点卡后，每一步都要在两处遭遇之间择一面对，遭遇分为战斗与非战斗（搜刮、陷阱、神龛献祭、低语的诱惑等）。事件描述只渲染征兆与氛围，不明说收益、伤害或是否开战，玩家只能凭直觉与对车厢特质的理解下注；部分车厢还会岔出特质更极端、掉落更专一的支线，供玩家为下一次配装主动绕路。

### Roguelike 元成长：把上一局的经验做成开局卡

每一局结束——无论通关还是倒在半路——都会结算经验，推动「守夜人等级」。升级解锁的不是数值加成，而是**一张会出现在下一局开局的卡**：强韧体魄提高生命上限，搏杀本能提高攻击，守夜警觉让你开局就戴着防毒面具，行囊与备粮多给几份材料，雾中拾遗直接塞给你一枚血晶。

把元成长表达为卡牌而不是数字，是为了保持世界观与界面的一致：玩家在结算页看到的是「新解锁的初始加成卡」，下一局开局时它就真的躺在你的牌桌上。

### LLM 运行时内容生成：把创意交给模型，把规则留在代码里

这个项目在技术上最核心的部分，是事件卡与敌人卡的**运行时 LLM 生成管线**。玩家每次进入一节车厢，事件与敌人可以不来自静态卡池，而是由模型即时写出来——但整条管线是被严格约束的：

* **结构约束**：只输出 JSON，禁止任何解释；每张事件必须声明 `kind`（战斗 / 普通），且 `kind` 必须与描述和结算结果一致——写成战斗就必须真触发战斗；批次里约一半战斗、一半普通。
* **内容白名单**：图标、可给出的物品、敌人定义 ID、行为 ID 全部来自白名单，并附带兼容表；掉落表由代码指定，模型不可自选。
* **数值主权在代码**：模型填写的 HP / 攻击只需落在给定 tier 区间内，实际数值以代码 roll 为准——**模型只负责文本质量**。
* **文风约束**：华丽、压抑、神秘、轻微克苏鲁；复古蒸汽朋克用词（铜锈、漆木、煤气灯、蒸汽、湿气、低语），禁现代词汇与出戏比喻；第二人称叙述；「异常被看见，但不被解释」。
* **防剧透模糊化**：标题与描述只写氛围与征兆，不得明说奖励、伤害或是否开战；战斗事件要贴合本副本敌人的形象，但不得直呼敌人全名、不得剧透结果。
* **二次校对 pass**：第一轮生成后再跑一遍「校对员」提示词，检查文风、模糊度、与敌人氛围的贴合度，并把与本局已给过的装备重复的掉落换成没给过的一件。
* **上下文感知**：生成时会带上玩家的 Build 倾向（火器路线、堆光克非人、近战利钝、裸拳流）、当前压力（长期低血）、近期选择与近期敌人，让文本贴着这一局的实际处境走。
* **降级与缓存**：生成结果进入缓存池，可「换血」刷新；请求超时或失败时静默降级回静态卡池，玩家不会看到报错，只会看到一张写得规矩些的卡。
